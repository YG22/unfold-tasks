- Signed-out users and signed-in users who have not chosen cloud keep localStorage data; cloud mode (per user, per device flag) uses useTaskStore: durable local cache + snapshot diff pushed via the transactional apply_task_changes RPC, realtime refetch with rebase, last-write-wins per record — why: no silent merge, offline-safe, retry-safe stable UUIDs. Local data is never deleted by migration.
- Planner calculations live in src/lib/planner/ as pure functions (half-open UTC intervals, ambiguous times resolve to the second occurrence like reminders); not wired into the app until a later stage — why: isolated, testable before UI/DB work.
- Planner cloud data lives in separate planner_* tables; clients may only SELECT their own rows, and every write goes through the SECURITY DEFINER apply_planner_changes RPC with per-record version checks, soft deletes, owner-scoped composite FKs and op_id-idempotent restores — why: stale offline edits and deleted records can never overwrite or resurrect data, and task sync stays untouched.
- Planner storage lives in src/lib/planner/{data,guest,sync,supabase}.ts: one row/model mapping and validation shared by guest (localStorage key planner-guest-v1) and cloud (per-user cache planner-cloud-v1-<uid>, ordered action queue with predicted base versions, quick edits merged before sending); conflicts and refused actions are stored, never auto-resolved; unreadable caches pause sync and are copied to a per-user recovery key; requests time out and are retried — why: retries stay idempotent and neither side is silently overwritten; not wired into screens yet.
- Guest-to-account planner migration lives in src/lib/planner/migrate.ts: read-only preview (fingerprints of cloud and guest data, relationship validation incl. split chains and cycles, blockers that need explicit resolutions), confirmation token, create-only actions (events/exceptions via apply_planner_changes' migrate_insert, which alone may write split history) sent in dependency order, deterministic per-account derived ids for collisions in every table (id_taken from migrate_insert; for categories/availability an "id already in use" refusal, safe because apply_planner_changes is one transaction, triggers a one-record-at-a-time resend) with remaps saved in the per-user journal planner-migration-v1-<uid>, preview compares records after remapping their references so an earlier run's remapped records count as already present even without the journal, full-field verification; guest data is never deleted — why: no automatic login migration, no silent overwrite or history loss, retries and resumes never duplicate; not wired into screens yet.
- Backup files are version 2 (src/lib/backup.ts) with an optional "planner" object handled by src/lib/planner/backup.ts: omitted sections are left unchanged, included (even empty) sections replace; guest restore is one localStorage write checked against the previewed content, cloud restore uses apply_planner_changes restore_preview/restore with previewed versions and one op_id; the planner is restored before tasks and tasks only if it succeeded — why: version 1 files stay valid, no silent overwrite, retries are safe; task and planner restores are not one atomic step.
